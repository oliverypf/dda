## 可复现的问题

下列命令从仓库根目录运行。定位时记录平台、Node/Git 版本、失败断言和首个异常事件。三个命令分别对应三个测试文件，可以单独复跑。

### 4 · CLI 批准后的执行

现有路径能发出审批请求、处理拒绝并核对显示给用户的摘要。失败的是三个批准路径：JSONL 以正确摘要批准、终端交互回答 y/n、通过实际 CLI 的 stdin 提交批准回复。现有证据只定位到 Windows 主机上的用例失败，尚未确定是回执、执行器、命令的平台差异，还是测试夹具所致。[终端审批](../linux-cli/src/terminal-approval.mjs) · [受控工具](../runtime/src/controlled-tools.mjs) · [失败用例](../linux-cli/test/controlled-approval.test.mjs)

- **定位**：运行 `node --test linux-cli/test/controlled-approval.test.mjs`。跟踪同一 requestId 的请求、批准回执、租约消费、命令输出与最终退出码，找到首个偏离预期的环节。
- **验收**：三种入口收到有效批准后各执行一次并返回预期输出；拒绝、错误摘要、输入提前结束均无命令执行。分别记录 Windows 复现环境和 Linux 原生环境结果。

### 5 · Git 元数据指纹误报

执行前后已有 Git 快照、作用域比较和审计检查点。失败用例在修改工作区文件后执行 `git status` 并更新 `FETCH_HEAD`；尚未暂存改动，元数据摘要就已变化。该断言先失败，因此需要另外验证后半段对真实暂存改动的检测。[Git 观察器](../runtime/src/git-observer.mjs) · [指纹回归](../runtime/test/git-audit.test.mjs)

- **定位**：运行 `node --test runtime/test/git-audit.test.mjs`。将工作区文件变化、索引缓存刷新、更新 FETCH_HEAD 拆开观测，找出引起摘要变化的输入。
- **验收**：普通工作区修改仍可见，索引缓存刷新和 FETCH_HEAD 更新不会单独触发越界；真实暂存或受监控配置变化仍能被发现。保留这两组相反结果，避免通过忽略整个索引来消除误报。

### 9 · 插件任务集成与资源隔离

签名校验、撤销、摘要校验和版本管理已有实现。复测中 ACTIVE 插件单独加载成功，随后运行完整任务时退出码为 1，失败点位于检查任务成功的断言。另有独立的设计差距：当前加载器在宿主中导入插件模块，插件状态置为 QUARANTINED 与限制已运行代码的系统访问是两种能力。[动态加载器](../runtime/src/plugin-loader.mjs) · [集成测试](../runtime/test/dynamic-plugin-runtime.test.mjs) · [隔离与资源规范](PLUGIN_SPEC.md)

- **先恢复集成回归**：运行 `node --test runtime/test/dynamic-plugin-runtime.test.mjs`。核对测试模型服务是否被实际选中，再检查任务退出原因和插件状态。验收时，ACTIVE 插件参与完整任务，停用或撤销的插件不被导入，单个插件失败有可查记录。
- **再实施隔离**：按可信级别确定允许的宿主 API 和隔离方式。验收覆盖申请范围外的资源访问被拒、超额插件可单独终止、宿主仍可处理下一任务。测试应能区分“拒绝加载”和“运行中强制限制”。

## 已有后端，仍需接通的路径

### 13 · 安全治理的逐级恢复

历史安全状态已能收紧工具门禁。`transitionRecover` 实现了逐级恢复、观测窗口和隔离状态的人工复核条件；基线的运行时源码中仅找到该函数定义。[恢复状态机](../runtime/src/safety-state.mjs) · [执行前门禁](../runtime/src/safety-spectrum-gate.mjs)

- **实施**：将明确的复核操作接到现有状态机，保存审查依据、适用对象和迁移结果，并让下一次工具调用读取新状态。
- **验收**：缺审查依据时保持隔离；满足条件后 QUARANTINE 只降到 DENY；重启后状态可恢复，重复提交同一审查不会再次降级。用实际工具调用核对新状态下的约束。

### 8 · 用户反馈进入模型路由

运行时已有反馈提交、评分、候选排名和演化控制，桌面能显示反馈记录。待接通的是用户提交、修订、撤回反馈后，其结果如何影响下一次同类任务的候选选择。[反馈存储](../runtime/src/feedback-registry.mjs) · [评分与排序](../runtime/src/bayesian-assessment.mjs) · [原设计 F1–F5](WINDOWS_BAYESIAN_FEEDBACK_DESIGN_PLAN.md)

- **实施**：先接通桌面操作到反馈事件及刷新，再将已有排名接到通过安全筛选的候选集。为每次排序保留适用场景、评分依据及实际选择。
- **验收**：同一反馈修订不重复计权，撤回后重新计算与事件回放一致；在同类任务中可观察排名变化，被安全筛除的候选始终不能入选。样本不足时能看出使用了哪条回退规则。

### 6 · 多 Agent 之间的相互质疑

Council 已并发调用规划和评论成员，再将候选交给裁决者。桌面能展示四个阶段。当前成员收到同一组初始输入，仍缺“读到另一成员的具体提案 → 针对该提案质疑 → 裁决引用回应”的一轮交互。[Council](../runtime/src/agent-council.mjs) · [桌面面板](../desktop/src/main.ts) · [审议协议设计](AGENT_HARNESS_DESIGN.md)

- **实施**：在独立提案和裁决之间增加有界的质疑阶段，关联被质疑的提案、证据和回应；沿用现有轮次、耗时或调用预算约束。
- **验收**：用两份存在分歧的提案，验证评论成员确实收到对方提案，裁决能指出采纳或排除哪条意见。无有效意见、超时、取消时均能结束，桌面只显示实际发生的阶段。

### 3 · Jev 的受限路由选择

已有任务分类、工具门禁、候选选择、计划评审和执行方式选择。具体缺口在 `SELECT_ROUTE`：当前主路径交给 Jev 的候选仅有保留或阻断既选路线。各决策开关和缺少凭据时的保守回退已有用途。[当前路由入口](../runtime/src/index.mjs) · [执行方式选择](../runtime/src/initial-topology-selection.mjs) · [决策层设计](JEV_DECISION_PLANE_DESIGN.md)

- **实施**：先确定哪些任务有两条以上合法路线，再由宿主列出通过安全筛选的候选及依据，将选中项传给后续调度并记录到 Decision Trace。
- **验收**：同一任务提供两条合法路线时，可从轨迹追到实际执行的选择；单候选、禁用、超时和非法返回均有可核对的行为。既有审批条件和硬拒绝仍生效。

## 用解题结果排优先级：与 DeepSeek Harness、BitFun、Pi 的机制对照

后续已完成 Git 指纹误报的四客户端同题实验，包含 12 次真实运行、逐轮工具记录、源码差异与独立行为判分。见[实验报告及 dda 三次停止位置](artifacts/git-fingerprint-2026-11-21/README.md)。

dda 已在可写的修复步骤中保留失败断言、目标命令和上一补丁，并在模型提前收尾时允许有界续修。改后三次独立验收通过两次，均在首次产品补丁后通过。错误补丁后的唯一一次红色复测触发了回读，第二个补丁仍未落盘；这段是下一项待验证的差距。[续修实验与执行记录](artifacts/git-fingerprint-retest-2026-11-21/README.md)

第二阶段将修复任务的源码改为按需加载，并将已读且版本相符的断言源码和上次实际补丁交还模型。从上述错误补丁和红灯开始的三次续跑均修改了产生指纹的实现，两次通过原测试和独立验收。余下一次虽找到了发生变化的文件，仍将存在性变化误判为内容哈希变化。最终验证器与外部行为判分的差异仍在。[断点续修的三份执行记录](artifacts/git-fingerprint-resume-2026-11-21/README.md)
