第 1 次在 #226、#236、#242、#250 查阅相关源码后直接提交了能保留区别的改动。提交前没有公开的因果说明；知道它保留了什么，依据是补丁、#280 的两项保留性检查和运行结束后的独立验收。[第 1 次记录](dda-1.json)

第 2 次的首份候选在 #273 退出 1，没有执行到受保护断言。#275 为 `unverified`，#276 的工具错误随下一个真实请求送达模型。按记录中的实际替换重建候选，单独运行 `node --check` 也报模块语法错误。第 13 轮模型才公开指出需要保留跨键和链接区别，并提交通过的方案。这一例说明它能在无效候选后重新修复，第一份候选的链接语义没有得到运行验证。[第 2 次记录及候选参数](dda-2.json)

第 3 次最能说明新增检查对执行路径的作用。首次候选直接从枚举清单移除 `FETCH_HEAD`。#372 显示原目标已经退出 0，#374 记录 `assertionPassed:true`，但宿主在该候选上无法核实原先测到的逐键区别，因此 #375 没有写入。该回执随第 4 个真实请求送达。第 12 轮模型明确说需要保留按键区分，随后 #506 回读生产者；下一份候选保留了这个键和链接类型。这里的反馈是“未核实原区别”的具体阻断，第一份候选没有单独接受事后两项验收，不能把它记作那两项的实测失败。[第 3 次记录、投递和预验](dda-3.json)

对上轮与本轮最终源码用同一套八项评分，上轮只有第 2 次全部通过，本轮三次全部通过。新增两项在本机采用真实 Git 仓库、真实产品观察器和受控的文件类型输入，逐项记录标注了原生文件链接权限错误 `EPERM` 及 `synthetic-lstat` 模式。三次 CLI 最终都因结论验证状态 `UNCERTAIN` 退出失败。[八项评分汇总](results.json) · [上轮决策](prior-decisions.md) · [独立验收与环境](multi-link/README.md)
