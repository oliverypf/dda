目前缺的环节，是把已经得到的两侧值用于检查**拟议补丁的结果**。第 1 次记录尤其清楚：知道“存在性会导致摘要变化”之后，仍把不同的两种类型写回同一个比较路径。第 2 次则表明即使两侧值已经正确推导，宿主仍会接受更多只检查文件的探针。两次之间共同缺少一次可核验的判断——按这份具体补丁各走一遍，进入摘要的值是否已满足原断言要求的关系。[第 1 次产品补丁](dda-1.patch) · [第 2 次工具与公开输出](dda-2.json)

## 旧第 2 次和第 3 次在哪里分开

两次都找到了会变化的磁盘文件。第 2 次看到 `FETCH_HEAD` 从缺失变为 67 字节，测了文件内容和观察器的最终摘要。它认为上一个补丁已经让易变文件“只记结构”，于是转去检查 hooks。这个结论缺少一步验证：两种状态下产生的结构是否相等。最后一次探针成功退出，原断言仍然失败。

第 3 次也曾转查 hooks。它后来按当时的生产源码重建了每个条目的序列化输入，才发现上一个补丁把存在时的值变成了 `{}`，而缺失分支仍提前返回 `{"exists":false}`。补齐这个分支后，原测试和独立验收都通过。记录能证实这次重建和修复，未记录生产进程内部的序列化缓冲区。详细的工具事件、代码和两份历史补丁见[旧两次的执行对照](divergence.md)。

## dda 改了什么

- 在补丁后的测试失败时，宿主从已验证的断言提取被比较的成员名，查找此前工具真正交付给模型的源码中同名的计算表达式。重新核对工作区权限、文件摘要和可见范围后，最多给出三个候选位置。每个位置都是供核对的源码线索。运行时的输入值仍需模型从实现推导或用探针测得。[续修实现](../../../runtime/src/repair-retest.mjs) · [已读范围核验](../../../runtime/src/plugins/workspace-readonly.mjs)
- 模型收到的下一步任务是对照两侧真正进入计算的值，指出第一处差异，再检查上一补丁对两侧各做了什么。两侧已可从代码和观察确定时可以直接修改。如果刚写的是诊断脚本，可以先运行它；如果改的是产品实现，就重跑原失败测试。[修复证据回归](../../../runtime/test/repair-assertion-source.test.mjs)
- 在补丁后复测仍红、旧历史足够大时，宿主把较早的完整工具轮次压成摘要，保留最近三轮原文、失败断言和上一补丁。旧试验断点首个真实请求为 119,030 字节，这次离线预检为 54,443 字节，正式三次分别为 54,434、54,448、54,449 字节，减少约 54.3%。请求中同时包含失败行 88、7,043 字符的旧补丁和已读生产代码中调用 `digestText(stableStringify(entries))` 的位置。两侧对象的值由模型自行确定。[上下文压缩](../../../runtime/src/context-compaction.mjs) · [压缩回归](../../../runtime/test/context-compaction.test.mjs)
