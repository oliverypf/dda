## 两种探针各自证明了什么

生产代码的调用链是 `observer.snapshot → readGitMetadata → readMetadataEntry → entries[name] → stableStringify(entries) → digestText`。第 2 次最终探针的 `describe` 单独对盘上文件做 `stat`、读取内容、取 SHA-256 前 12 位，只在快照层调用真实观察器。两端各自回答了“哪个文件变了”和“总摘要是否变了”。对照第 2 次的最终源码，缺失时提前返回 `{exists:false}`，已存在的普通易变文件返回 `{exists:true,type:"file"}`。即使不读内容，序列化这两个对象也会产生不同的输入。[第 2 次产品及探针 diff](../git-fingerprint-resume-2026-11-21/dda-2.patch) · [断点时的生产源码和工具记录](../git-fingerprint-resume-2026-11-21/dda-2.json)

第 3 次的 `tmp-observer-probe.mjs` 调用了真实的 `observer.snapshot`。`tmp-meta-entry-probe.mjs` 则在临时仓库中按当时的源码重写了 `entry` 和 `snapshotMetadata`，用 `JSON.stringify` 比较每一项。它截短了内容哈希，也独立实现了 hooks 枚举。事件 #1444 证明脚本执行成功，具体的值对来自随后公开说明，与脚本的缺失、存在两个返回分支相符。原测试和外部验收验证了补上缺失分支后的行为。现有记录没有直接截获生产函数内部的序列化缓冲区。[第 3 次四个探针和最终补丁](../git-fingerprint-resume-2026-11-21/dda-3.patch) · [公开归因及回执](../git-fingerprint-resume-2026-11-21/cause-observations.json)

## 在原剩余预算内，最早可以怎么分流

最早在接手第 88 行时就可以顺着失败值回到生产者，列出比较两端分别走哪条返回路径。第 2 次 #1112 是已经拿到物理变化后的明确分流点。此时先从当前源码算出候选字段在两侧的实际值，再用一次能成对输出中间记录的观察核对；若这一对相同，再扩大到其他字段。这里应优先检查缺失时的提前返回。写入临时诊断脚本后，直接执行它就能取得这份证据。仅凭脚本退出 0，还需要看它比较的具体值。[第 2 次说明与后续补丁](../git-fingerprint-resume-2026-11-21/cause-observations.json)

这两条历史轨迹中，第 2 次前五、前六个真实请求累计分别为 645,070 和 783,835 字节，第 3 次分别为 635,904 和 777,586 字节。按原断点剩余的 711,126 字节，两条轨迹都只够前五个请求。由此得到的实现目标是把“上次补丁预测两边应该相同，哪两个实际输入能证伪这条预测”提前到首条续修提示，复用已经读过的源码，尽量在一次观察里比较两端。两条历史轨迹只能说明这个分流点和代价，改后稳定性应由同余额下的三次新运行验证。[第 2 次逐请求字节](../git-fingerprint-resume-2026-11-21/dda-2.json) · [第 3 次逐请求字节](../git-fingerprint-resume-2026-11-21/dda-3.json)
