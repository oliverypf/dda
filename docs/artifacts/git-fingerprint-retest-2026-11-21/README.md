# dda 复测失败后的续修实验

2026-11-21。Git 指纹误报题的独立验收从 **0/3 提高到 2/3**，留下产品源码补丁的尝试从 1/3 增至 3/3。两次通过都发生在第一个产品补丁之后。最需要验证的情形是“错误补丁落盘，复测仍红，再做第二个有效补丁”。改前和改后各遇到一次，两次都没走到第二个补丁。[改前报告](../git-fingerprint-2026-11-21/README.md) · [改后逐轮评分](results.json)

## 执行逻辑

在允许写入的修复步骤中，执行器从真实测试回执提取命令、工作目录、失败断言和栈帧，并关联当时最近一次成功的文件写入。对于 `file.patch`，上下文还包括有长度限制的新增行和删除行。测试仍红时，下一轮要把断言检查的值追到产生它的实现，对照之前的修改，选择一个能区分原因的观察或一个有依据的改动。又有新补丁时，优先重跑原目标。同一命令及参数、同一目录的成功回执可以清除对应失败，单跑一个成功的诊断脚本会保留原失败。[续修状态](../../../runtime/src/repair-retest.mjs) · [执行循环](../../../runtime/src/plugins/task-runner.mjs)

模型在仍有失败时写总结，宿主会提示它执行下一步，或指出具体阻塞。对同一份证据只退回一次，单次执行最多退回两次，并受原有轮数、权限及停止条件限制。集成回归覆盖了错误补丁后用第二个补丁跑绿、中间插入无关绿测、再改却漏测、持续只汇报红灯，以及仅检查旧补丁。使用预设工具响应的回归可以稳定触发提前收尾分支。[回归测试](../../../runtime/test/task-runner-tools.test.mjs)

## 本次改善到哪一步

两次绿色尝试都追到了指纹的产生处，修复了普通易变文件从缺失到出现时导致摘要变化的问题。两份补丁的质量也有差别。静态复核显示，第 1 次跳过了这两个路径的类型检查，连已有的符号链接信号也会丢失；第 3 次保留了该信号。原评分没有符号链接用例，以上差异单列，不改变预先约定的分数。补丁均保存在实验工作区。[第 1 次补丁](dda-1.patch) · [第 3 次补丁](dda-3.patch)

唯一真正检验补丁后续修的是改后第 2 次。模型先改了消费指纹的比较逻辑，而第 88 行断言直接比较指纹本身。宿主识别出了这次反证，模型随即两次读回断言，但没有转到生成该值的实现。三次实跑的 `harness.repair_continued` 事件数均为零，因而外部通过率的上升不能归因于退回收尾草稿。后续可用这一段作固定回放，单独统计“补丁后仍红 → 根据断言找到产生该值的实现 → 作出不同的补丁 → 原命令跑绿”，并记录红灯出现时还能发多少请求字节。[第 2 次补丁](dda-2.patch) · [第 2 次事件及代理记录](dda-2.json)

### 同一字节预算能支持多少次决策

用原生客户端、原题面和新种子副本做首请求测量。本地接收端计数后立即返回，未访问上游模型。实际 HTTP 请求体长度与历史代理账本一致。下表按序列化后的 UTF-8 字节计数，工具列包含整份工具声明。[字段计数及预读文件清单](pi-context-evidence.json)

| 首请求 | 总字节 | 整份工具声明 | 工作区快照文本 |
| --- | ---: | ---: | ---: |
| dda | 178,672 | 12,946，10 个工具 | 161,342，占 90.3% |

dda 的快照有 200 个目录项，18 份文件的标题和正文占 149,253 字节。故障实现和目标测试都没有入选，模型随后仍需调用工具读取它们。改后 dda 第 2 次收到红灯时，预算还剩 711,126 字节。接下来两个请求分别占 259,117 和 261,451 字节，余下 190,558 字节装不下下一个请求。两次读工具都只返回了短窗口，实验的字节上限计算每轮发出的整个请求体。[快照采集](../../../runtime/src/plugins/workspace-readonly.mjs) · [发送快照的执行循环](../../../runtime/src/plugins/task-runner.mjs) · [逐请求账本](dda-2.json)

### 现有续修提示缺了什么

第 88 行执行 `assert.equal(before.metadataDigest, afterRefresh.metadataDigest)`，对比较函数的调用在它之后。用第 2 次留下的工作区重跑原命令，再用真实 diff 和输出重建续修提示，其中有第 88 行的栈帧、实际值、期望值及上一次补丁的片段，断言摘录里没有字段名或这行源码。执行器给模型的第一项提示仍是去读断言。[本地回放](pi-context-evidence.json) · [提示构造](../../../runtime/src/repair-retest.mjs)

本次 dda 的第 1 轮其实已读到整份测试。按原参数重放三次读取，工具回执摘要均匹配历史。红灯后第一次回读覆盖第 46–71 行，第二次才覆盖第 71–101 行。两次窗口不同，只有第二次包含第 88 行。`workspace.read` 支持字符偏移和字面搜索，栈帧给出的却是行号。程序可以直接从已读版本摘出断言，省下模型猜偏移的往返。[dda 读工具](../../../runtime/src/tool-registry.mjs) · [读取参数、行号与回执摘要](pi-context-evidence.json)

下一次实现可以用同一份错误补丁和红色回执做两项独立验收。

1. 将修复任务开场预读的文件正文改为按需加载，保留项目概况及路径索引。记录首包大小、失败后的每轮请求大小，以及首次观测产生错误值的实现时累计用了多少字节。
2. 已读版本与当前文件一致时，把栈帧对应的断言行及附近代码连同上次补丁交还执行器。下一轮应定位该值的来源或做区分原因的探针。最终以新的产品补丁、同一测试由红转绿和独立验收通过判定续修成功。用干净种子直接一次改对，单列为首次修复。

这两处随后均已实现。从本报告第 2 次的错误补丁和红灯接手，三次都写出了后续产品补丁，两次通过六项验收，其中一次又修正了自己的失败补丁。按旧断点剩余请求字节观察，一次在该阈值内跑绿。[断点续修与独立验收](../git-fingerprint-resume-2026-11-21/README.md)
